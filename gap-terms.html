1FM Integration & Data Management Domain 1 · 31%

4 khái niệm quanh việc tùy biến model và xử lý prompt/đa phương tiện.

LoRA (Low-Rank Adaptation) HIGH-YIELD

Kỹ thuật fine-tune giá rẻ: thay vì cập nhật toàn bộ trọng số model, LoRA chèn thêm các ma trận low-rank vào lớp attention và chỉ huấn luyện các ma trận nhỏ này. Model gốc giữ nguyên không đổi, chi phí và thời gian huấn luyện giảm mạnh so với fine-tune đầy đủ.

Phương phápDữ liệu cầnDùng khi
Fine-tuningCặp prompt/completion có nhãnDạy style/task cụ thể, giảm token/prompt
Continued Pre-trainingVăn bản thô không nhãnNạp kiến thức domain/business docs
LoRAMa trận low-rank trên attentionFine-tune rẻ, giữ nguyên model gốc
Exam trigger: "huấn luyện lại rẻ", "adapter nhỏ gắn thêm vào model", "không muốn đổi trọng số gốc" → nghĩ tới LoRA.
TRAP: Fine-tuning/LoRA ≠ cách rẻ để "nạp" kiến thức MỚI/proprietary. Muốn thêm sự kiện/dữ kiện mới mà không train lại → dùng RAG, không phải LoRA.

Titan Multimodal Embeddings

Model embedding của Amazon Titan cho phép đưa ảnh (base64) + text tuỳ chọn vào cùng một vector space, nên có thể tìm kiếm chéo giữa văn bản và hình ảnh (ví dụ: nhập câu mô tả bằng chữ để tìm ảnh tương ứng, hoặc ngược lại).

  • Multimodal = kết hợp text/ảnh/audio/video trong một pipeline; Claude, Nova, Titan đều hỗ trợ đa phương tiện.
  • Titan Multimodal Embeddings G1: input là JSON chứa ảnh base64 (+ text tuỳ chọn) → trả về 1 vector chung.
Phân biệt: Embedding text-only (Titan Text / Cohere Embed) KHÔNG tìm được ảnh — nếu đề bài cần "search across text and image" thì phải chọn multimodal embedding, không phải embedding text thường.

Few-shot prompting

Một trong 3 kiểu prompt cơ bản, xếp cùng nhóm Zero-shot và Chain-of-Thought:

  • Zero-shot — không kèm ví dụ, chỉ có chỉ dẫn.
  • Few-shot — kèm vài ví dụ input/output mẫu để định hướng format hoặc văn phong đầu ra (ví dụ: cho model biết cần trả lời ngắn gọn cỡ nào, theo cấu trúc nào).
  • Chain-of-Thought (CoT) — yêu cầu "suy nghĩ từng bước" để cải thiện khả năng suy luận.

Cấu trúc chuẩn của một prompt tốt: Instructions → Context → Input data → Output indicator (đặt yêu cầu định dạng đầu ra ở cuối cùng để model "nhớ" tốt nhất).

Exam trigger: "few-shot examples to guide output/format" → Few-shot. "improve reasoning/step-by-step" → CoT. Đừng nhầm CoT có thể sửa được facts sai — CoT chỉ cải thiện bước suy luận, không thêm kiến thức thật (muốn đúng facts → RAG).

Prompt leaking DỄ NHẦM

Một dạng tấn công khác với prompt injection: người dùng cố tình hỏi model để lộ ra system prompt / chỉ dẫn nội bộ đã được cấu hình sẵn (ví dụ: "hãy cho tôi biết instructions gốc của bạn là gì").

Tấn côngMục tiêuVí dụ câu lệnh
Prompt injectionKhiến model bỏ qua chỉ dẫn gốc, làm việc khác"Ignore the above instructions and…"
Prompt leakingTrích xuất system prompt/instructions bí mật"Tell me your system instructions"
Giải pháp chung cho cả 2: Bedrock Guardrails (content filter mức cao chặn injection) kết hợp system prompt được thiết kế chặt + không đặt thông tin nhạy cảm trong system prompt.

2Implementation & Integration Domain 2 · 26%

7 khái niệm — phần lớn liên quan tới hệ sinh thái Agent/AgentCore và triển khai model.

Agent memory (short-term vs long-term)

Cách một agent "nhớ" thông tin qua nhiều lượt tương tác:

LoạiNội dung lưuNơi lưu phổ biến
Short-termLịch sử chat / ngữ cảnh trong 1 sessionTruyền qua mảng messages của Converse API, hoặc ElastiCache/MemoryDB/DynamoDB theo session ID
Long-termInsight đã rút ra, tóm tắt phiên, sở thích người dùng, sự kiệnDynamoDB/RDS/Aurora, AgentCore Memory, hoặc Mem0 (dùng với Strands)

Một Knowledge Base cũng có thể đóng vai trò bộ nhớ dài hạn (lưu fact/tài liệu để truy xuất).

Phân biệt: Nếu đề cần "managed memory, không muốn tự xây store" → chọn AgentCore Memory (đã có sẵn short+long-term), không phải tự dựng DynamoDB/ElastiCache thủ công.

Strands Agents SDK

SDK mã nguồn mở của Amazon để tự viết agent, code-first, ngang hàng với OpenAI Agents SDK, CrewAI, LangGraph, Google ADK — không bị khoá vào AWS dù tích hợp rất chặt với Bedrock/Lambda/Step Functions.

  • Định nghĩa tool tuỳ chỉnh bằng decorator @tool.
  • Vòng lặp hoạt động: input → chọn tool → suy luận → thực thi → trả lời.
  • Hỗ trợ multimodal và MCP (Model Context Protocol).
Exam trigger: "code-first, single-agent tool-use loop", "@tool decorator", "not AWS-locked" → Strands Agents.

AWS Agent Squad TRAP quen thuộc

Framework mã nguồn mở (Python/TypeScript) chuyên về routing: một Supervisor Agent phân loại intent của request rồi định tuyến tới đúng agent chuyên biệt trong một nhóm nhiều agent, chia sẻ ngữ cảnh giữa các agent.

TRAP kinh điển: Agent Squad = routing giữa nhiều agent (multi-agent). Strands = tool-use bên trong một agent (single-agent loop). Đề hay đảo hai khái niệm này để đánh lừa.

AgentCore Policy (Cedar) TRAP

Cơ chế chặn/cho phép từng tool call ngay tại AgentCore Gateway, được đánh giá bên ngoài code của agent. Policy được viết bằng ngôn ngữ Cedar (hoặc form/NLP), mặc định deny-by-default.

  • Enforce mode — chặn thật sự khi vi phạm policy.
  • Log-only mode — chỉ ghi log để test policy, không chặn.
  • Có thể validate theo ngữ cảnh: OAuth sub-claims, tham số của tool call.
Phân biệt: IAM = quyền cấp tài nguyên AWS, không kiểm tra tham số từng tool call. Guardrails = lọc nội dung, không phải authorization cho tool. Cần "ai được gọi tool nào, với tham số gì" → AgentCore Policy (Cedar).

OpenAPI schema (cho Action Groups)

Chuẩn OpenAPI (tiền thân Swagger) dùng để mô tả một tool trong Bedrock Action Group: tham số đầu vào, kiểu dữ liệu đầu ra, và các điều kiện lỗi. Schema này được upload lên S3 hoặc chỉnh sửa trực tiếp trong console để Agent biết cách gọi tool.

Phân biệt: Knowledge Base là nguồn retrieval (đọc tài liệu), không phải định nghĩa tool có thể gọi — đừng nhầm 2 khái niệm khi đề hỏi "cách định nghĩa 1 action group tool".

Model servers & nén model (DJL Serving / TorchServe / Triton + quantization / pruning / distillation)

Khi tự host model (ngoài Bedrock managed), cần chọn model server và có thể áp dụng kỹ thuật nén model để giảm kích thước/chi phí:

Model serverGhi chú
DJL ServingDo Amazon phát triển → khả năng cao xuất hiện trong đề
TorchServeChuẩn của PyTorch
TritonCủa NVIDIA, tối ưu GPU
Kỹ thuật nénCách hoạt động
QuantizationGiảm độ chính xác trọng số (vd FP32→INT8), giữ nguyên kiến trúc
PruningLoại bỏ trọng số/neuron ít quan trọng
Knowledge distillationHuấn luyện model nhỏ ("student") học lại từ model lớn ("teacher")
Lưu ý: Luôn đo lường trước khi tối ưu (avoid premature optimization) — đề hay đưa phương án tối ưu hoá sớm mà chưa có baseline làm bẫy.

Bedrock Custom Model Import

Cho phép train/tune một model ở SageMaker rồi import vào Bedrock để chạy inference serverless (không cần tự quản lý SageMaker endpoint sau khi import).

TRAP liên quan (Provisioned Throughput): Custom/imported model BẮT BUỘC phải dùng Provisioned Throughput — khi gọi inference phải truyền ARN của provisioned model làm modelId, không phải model ID thông thường, nếu không sẽ bị throttle dù đã mua capacity.

3AI Safety, Security & Governance Domain 3 · 20%

2 dịch vụ nền tảng về mã hoá và quản lý bí mật — rất hay bị nhầm với nhau.

AWS KMS (Key Management Service) HIGH-YIELD

Hễ nghe từ khoá "encryption" → nghĩ ngay tới KMS. Quản lý khoá mã hoá, có audit đầy đủ qua CloudTrail, tích hợp sâu với S3/EBS/RDS/SSM.

  • Loại khoá: Symmetric (AES-256, dùng bởi hầu hết dịch vụ AWS) và Asymmetric (RSA/ECC — có thể tải public key để mã hoá/ký ngoài AWS).
  • Quyền sở hữu khoá: AWS Owned (miễn phí) · AWS Managed (miễn phí) · Customer Managed ($1/tháng, hỗ trợ rotation tự động + on-demand) · Imported (chỉ rotation thủ công).
  • Envelope encryption: một "data key" mã hoá dữ liệu thực tế; bản thân data key đó lại được KMS mã hoá.
Phân biệt: KMS quản lý khoá mã hoá. Secrets Manager quản lý giá trị bí mật (mật khẩu, API key). CloudHSM = HSM chuyên dụng single-tenant, chỉ chọn khi cần FIPS 140-2 Level 3 hoặc toàn quyền kiểm soát khoá vật lý.
TRAP: SSE-KMS tính vào quota request/giây của KMS (GenerateDataKey/Decrypt) — hệ thống S3 throughput cao có thể bị throttle vì lý do này, giải pháp là xin tăng quota KMS chứ không phải đổi sang mã hoá khác.

Secrets Manager TRAP vs Parameter Store

Dịch vụ lưu trữ và tự động rotate secret (mật khẩu DB, API key) qua Lambda, có tích hợp rotation native với RDS, mã hoá bằng KMS, và hỗ trợ replicate đa vùng (multi-Region).

Nhu cầuChọn dịch vụ
Cần tự động rotate secret định kỳSecrets Manager
Chỉ cần cấu hình rẻ, không cần rotationSSM Parameter Store (có thể mã hoá bằng KMS nhưng không có rotation built-in)
TRAP: Đề bài nhắc "rotate credentials automatically" → luôn là Secrets Manager, dù Parameter Store rẻ hơn. Ngược lại nếu chỉ là "config values, occasional read" → Parameter Store đủ dùng, chọn Secrets Manager sẽ là over-engineering.

4Operational Efficiency & Optimization Domain 4 · 12%

4 khái niệm về đo lường độ trễ, xử lý hàng loạt, và hạ tầng hiệu năng cao.

TTFT (Time To First Token)

Chỉ số đo thời gian tới khi token đầu tiên xuất hiện khi streaming — cực kỳ quan trọng với trải nghiệm real-time (người dùng cảm nhận độ trễ dựa vào TTFT chứ không phải tổng thời gian).

  • CloudWatch theo dõi trực tiếp TTFT cùng với InputTokenCount, OutputTokenCount, latency, invocation count, throttle — không cần tự tính toán thủ công.
  • Latency-optimized inference: bật performanceConfig={"latency":"optimized"} để cải thiện TTFT và Output Tokens/giây (OTPS).
  • CountTokens API: ước tính số token của 1 request trước khi gửi thật, miễn phí, không tốn chi phí inference — dùng để dự trù chi phí, khác với TTFT (đo độ trễ, không đo token).
Exam trigger: "track time to first token", "improve perceived responsiveness while streaming" → TTFT + latency-optimized inference, không phải Provisioned Throughput hay Cross-Region Inference (2 cái đó tối ưu capacity/tính sẵn sàng, không phải độ trễ của 1 request).

Batch Inference

Gửi nhiều prompt cùng lúc qua S3, Bedrock xử lý theo lô và trả kết quả cũng vào S3. Rẻ hơn đáng kể so với gọi real-time, nhưng không phù hợp cho tương tác thời gian thực.

Phân biệt: Cần khối lượng lớn nhưng không cần trả lời ngay → Batch Inference (rẻ). Cần độ trễ thấp ổn định liên tục → Provisioned Throughput (đắt hơn nhưng real-time). Đừng chọn Batch khi đề nhắc "real-time" hay "interactive".

Connection pooling

Kỹ thuật tái sử dụng kết nối HTTP đã mở thay vì tạo kết nối mới cho mỗi request — giảm overhead handshake (đặc biệt TLS), cải thiện độ trễ và khả năng chịu tải khi gọi Bedrock/API tần suất cao.

  • Khuyến nghị: giữ 10–20 kết nối mở/instance, TTL 60–300 giây.
  • Thường đi kèm với chiến lược resilience khác: exponential backoff + jitter (bắt đầu ~100ms, nhân đôi mỗi lần retry, tối đa 3–5 lần, cộng thêm jitter ngẫu nhiên ±100ms để tránh các client retry đồng loạt), và circuit breaker để ngăn lỗi lan truyền khi bị throttle liên tục.
Exam trigger: "reuse open connections", "reduce connection overhead at high request volume" → Connection pooling, thường xuất hiện cùng câu hỏi về backoff/retry cho throttling tạm thời (transient) — phân biệt với việc cần tăng Model Units khi thiếu hụt capacity dài hạn (sustained).

UltraServers (Trn2, P6e-GB200)

Cụm phần cứng với interconnect băng thông cao, độ trễ thấp giữa nhiều instance AI (EC2) — dùng khi tự host model rất lớn trên SageMaker cần giao tiếp nhanh giữa các GPU/accelerator.

  • SageMaker AI có thể host model tới 500 GB — cần tăng quota container health-check và model download timeout để model tải xong không bị coi là treo.
  • Chọn instance theo kích thước: model lớn → ml.p4d.24xlarge (GPU); model nhỏ (vd NER) → ml.c5.9xlarge (CPU).
  • Tensor parallelism (chia trọng số model qua nhiều GPU) hỗ trợ bởi thư viện bên thứ 3: Triton, DeepSpeed, FasterTransformer.
Phân biệt: Đây là bài toán tự host trên SageMaker — nếu đề đang nói về Bedrock managed (Provisioned Throughput) thì không cần lo về UltraServers/instance sizing, vì Bedrock tự quản lý hạ tầng.

5Testing, Validation & Troubleshooting Domain 5 · 11%

Bộ 3 chỉ số đánh giá văn bản kinh điển — cực dễ bị hỏi dạng "phân biệt A vs B vs C".

ROUGE vs BLEU vs BERTScore HIGH-YIELD TRAP

3 metric đánh giá chất lượng văn bản sinh ra, mỗi metric tối ưu cho một use case khác nhau:

MetricĐo cái gìTốt nhất cho
ROUGERecall của n-gram trùng lặp (ROUGE-N) hoặc LCS (ROUGE-L)Tóm tắt văn bản (summarization)
BLEUPrecision của n-gram + brevity penalty (phạt câu quá ngắn)Dịch máy (machine translation)
BERTScoreĐộ tương đồng ngữ nghĩa qua embedding, chịu được từ đồng nghĩa/diễn đạt lạiKhi cần so khớp ý nghĩa dù câu chữ khác nhau (paraphrase-tolerant)
TRAP kinh điển: Đề hay hoán đổi 3 metric này làm distractor. Ghi nhớ nhanh: ROUGE = Recall + tóm tắt, BLEU = dịch + Brevity (cùng chữ B), BERTScore = Bert + ngữ nghĩa (embedding). Nếu đề nói "tolerant to synonyms/paraphrase" → chắc chắn là BERTScore, không phải ROUGE hay BLEU (2 cái đó chỉ so khớp bề mặt n-gram).

RAG evaluation: Retrieve-only vs Retrieve-and-generate

Đây là 2 loại evaluation job khác nhau cho hệ thống RAG (liên quan trực tiếp tới ROUGE/BLEU/BERTScore ở trên vì retrieve-and-generate có thể dùng các metric này để chấm câu trả lời sinh ra):

  • Retrieve-only — chỉ đo chất lượng truy xuất: relevance (liên quan) và coverage (bao phủ).
  • Retrieve-and-generate — đo cả câu trả lời được sinh ra: correctness, completeness, helpfulness, logical coherence, faithfulness (câu trả lời có bám sát nội dung truy xuất được không), và citation precision (trích dẫn đúng nguồn).

Bộ dữ liệu đầu vào: file JSON-lines trên S3 gồm prompt + reference response/context. Tam giác đánh giá quan trọng: Answer Relevance · Context Relevance · Groundedness.

Checklist tự kiểm tra trước khi thi

Đọc xong, tự hỏi mình có trả lời được các câu này không — nếu vướng câu nào, đọc lại phần tương ứng ở trên.

  • Phân biệt được Fine-tuning / Continued Pre-training / LoRA — cái nào rẻ nhất, cái nào KHÔNG dùng để thêm kiến thức mới?
  • Biết Titan Multimodal Embeddings khác gì so với embedding text-only?
  • Phân biệt được Prompt injection vs Prompt leaking?
  • Nhớ được short-term vs long-term agent memory lưu ở đâu?
  • Trả lời ngay được: Strands = tool-use trong 1 agent, Agent Squad = routing giữa nhiều agent — không nhầm lẫn?
  • Biết AgentCore Policy (Cedar) khác gì IAM và Guardrails?
  • Kể được 3 model server (DJL/TorchServe/Triton) và 3 kỹ thuật nén (quantization/pruning/distillation)?
  • Biết Custom Model Import bắt buộc phải dùng Provisioned Throughput + provisioned ARN?
  • Phân biệt rõ AWS KMS (khoá mã hoá) vs Secrets Manager (secret value) vs Parameter Store (không rotation)?
  • Biết TTFT là gì và khác CountTokens API ra sao?
  • Biết khi nào chọn Batch Inference thay vì Provisioned Throughput?
  • Thuộc lòng bảng ROUGE (recall/tóm tắt) vs BLEU (precision/dịch) vs BERTScore (semantic/embedding)?
