Amazon Bedrock — nền tảng cốt lõi HIGH-YIELD

API serverless để gọi nhiều foundation model (Titan/Nova, Claude, Llama, Mistral, Cohere, Stable Diffusion, Jurassic-2) qua chat/text/image, dùng model pre-built/fine-tuned/imported. Model bên thứ 3 vẫn tính phí qua AWS theo giá riêng của họ. Tích hợp sẵn với SageMaker Canvas.

  • Luôn dùng IAM user (không dùng root) với policy AmazonBedrockFullAccess / …ReadOnly.
"cần 1 API serverless để gọi nhiều FM (Claude/Titan/Llama)" → Amazon Bedrock.
Muốn tự host/train model từ đầu → SageMaker, không phải Bedrock.

Bedrock API endpoints & Converse HIGH-YIELD

  • bedrock: quản lý/deploy/train model · bedrock-runtime: inference (Converse, InvokeModel, …Stream).
  • bedrock-agent: quản lý agent + KB · bedrock-agent-runtime: InvokeAgent, Retrieve, RetrieveAndGenerate.

"truyền messages array để giữ context" / "interface nhất quán giữa các model" → Converse. "stream phản hồi từng ký tự" → InvokeModelWithResponseStream.

TRAP: Fine-tuning ≠ cách rẻ để thêm kiến thức mới. Muốn thêm facts mới/proprietary → dùng RAG, cập nhật một DB rẻ hơn train lại.

RAG vs Fine-tuning (quyết định chọn cái nào) HIGH-YIELD

RAG = "open-book exam": truy xuất từ DB rồi chèn vào prompt, không phải training. Chọn RAG khi cần dữ liệu mới/proprietary, cập nhật rẻ, "AI search" ngữ nghĩa, giảm hallucination.

Fine-tuning dạy style/format đầu ra, KHÔNG thêm kiến thức mới — chọn sai nếu đề cần facts mới.
Lưu ý: RAG vẫn non-deterministic, nhạy với prompt template và độ liên quan khi truy xuất — vẫn có thể hallucinate nếu retrieval kém.

Embeddings & vector search

Embedding = 1 vector; item tương tự nằm gần nhau trong không gian vector. Retrieval: embed câu hỏi → tìm top-N gần nhất (k-NN) → trả kết quả. Cosine similarity là thước đo phổ biến nhất.

  • Dense embedding (nhỏ, ngữ nghĩa) là mặc định; sparse (lớn, one-hot) cho độ chính xác sắc hơn nhưng kém hiệu quả hơn.
  • Tính embedding bằng Titan / Cohere.
Cần khớp từ khóa/tên viết tắt chính xác → keyword hoặc hybrid search, không phải pure embedding.

Bedrock Knowledge Bases (managed RAG) HIGH-YIELD

  • Ingest từ S3 (JSON schema), web crawler, Confluence, Salesforce, SharePoint.
  • Cần embedding model (Cohere/Titan) bạn có quyền truy cập; tự chọn vector dimension + chunking.
  • Vector store mặc định = OpenSearch Serverless; ngoài ra Aurora (pgvector), MemoryDB, MongoDB Atlas, Pinecone, Redis, S3 Vectors.
  • "Chat with your document" = RAG tự động; nhúng vào app hoặc agent ("agentic RAG").
"KB dựa trên S3", "metadata-aware filtering", "RetrieveAndGenerate trả citation", "Graph RAG với Neptune Analytics" → Bedrock Knowledge Bases.
Tự dựng pgvector/OpenSearch (DIY embedding pipeline) = nhiều overhead vận hành hơn KB managed.

Vector store: S3 Vectors vs OpenSearch HIGH-YIELD TRAP

  • S3 Vectors: rẻ hơn ~90%, đơn giản, strongly consistent; độ trễ chỉ 100ms–1s. Tối đa 10k index/bucket, 2B vector/index. Batch 500/lần gọi.
  • OpenSearch: backend KB chính của đề thi; nhanh, hỗ trợ semantic + hybrid search và tuning.
  • "Tiered search" của AWS: vector lạnh/ít dùng ở S3 Vectors, vector nóng/perf-critical ở OpenSearch.
Vector rẻ/lạnh/ít truy cập, chấp nhận 100ms–1s → S3 Vectors. Cần lọc metadata phong phú/hybrid/độ trễ thấp → OpenSearch.
TRAP hay ra đề: Tích hợp S3 Vectors → OpenSearch sẽ COPY dữ liệu sang OpenSearch — nếu không cẩn thận bạn trả tiền cho CẢ HAI.

OpenSearch làm vector store TRAP

  • ANN engine: FAISS, NMSLib, Lucene. HNSW = nhanh/recall cao, tốn RAM; IVF = dataset khổng lồ, đổi recall lấy tốc độ/bộ nhớ.
  • Tuning: M (số cạnh/node), ef_construction (build graph), ef_search (độ sâu tìm kiếm) — càng cao recall càng tốt nhưng chậm/tốn RAM hơn.
  • Semantic = vector search · Hybrid = vector + keyword (cần field keyword đã index để filter).
  • Nén: binary vector (nhỏ hơn 32× so với float32), FP16 scalar quantization.
"search bỏ sót từ khóa/thuật ngữ y khoa chính xác nhưng trả kết quả tương tự ngữ nghĩa" → cần hybrid search (vector + keyword), không chỉ pure vector k-NN.
TRAP: OpenSearch Serverless KHÔNG scale về 0 — phải tắt khi không dùng nếu không sẽ vẫn bị tính phí.

Giữ Knowledge Base luôn mới (fresh)

S3 object mới/thay đổi → event trigger → Lambda → StartIngestionJob để re-embed. Batch tạo embedding hoặc chạy theo lịch để tiết kiệm hơn so với sync mọi thay đổi.

KHÔNG cần retrain FM để làm mới dữ liệu — chỉ cần re-ingest KB.

Bedrock Data Automation (BDA) HIGH-YIELD

  • Trích xuất dữ liệu có cấu trúc từ mọi loại: tài liệu, ảnh, video, audio (multi-modal IDP).
  • Docs: PDF/TIFF/JPEG/PNG/DOCX → JSON (+CSV/markdown/HTML). Độ chi tiết: page / element (mặc định) / word.
  • Blueprints định nghĩa field cần trích (chuẩn như US Driver License, hoặc tự tạo — kể cả từ 1 prompt).
  • Khởi chạy qua InvokeDataAutomationAsync với 1 Project (chứa nhiều blueprint).
Textract chỉ xử lý tài liệu/form; BDA còn bao phủ cả ảnh/video/audio.

Data-prep & dịch vụ NLP

Tiền xử lý TRƯỚC khi vào Bedrock: Comprehend (PII/NER/toxicity), Transcribe (giọng nói→văn bản), Textract (tài liệu scan), Glue (ETL/Data Quality).

  • AWS Glue: ETL serverless + Data Catalog (crawler tự build schema, dữ liệu vẫn ở S3). Glue Data Quality dùng ngôn ngữ DQDL.
  • Comprehend: NLP — phân loại tuỳ chỉnh, NER, custom entity, phát hiện PII. Comprehend Medical = HIPAA, DetectPHI.
  • Transcribe: ASR (speech→text), redact PII, custom vocab + custom language model để tăng độ chính xác.
  • Pattern quen thuộc: Lambda + Comprehend để redact PII/phân loại trước khi dữ liệu chạm Bedrock hoặc KB.
Bedrock Guardrails lọc PII ở thời điểm inference; muốn redact PII trong dữ liệu NGUỒN → dùng Comprehend.

Pipeline đa phương tiện (Multimodal)

Multimodal = kết hợp text/ảnh/audio/video; Claude, Nova, Titan đều hỗ trợ. Model embedding đa phương tiện ánh xạ nhiều loại media vào 1 vector space chung — có thể search bằng bất kỳ input nào.

  • Titan Multimodal Embeddings G1: truyền JSON kèm ảnh base64 (+ text tuỳ chọn).
Embedding chỉ-text (Titan/Cohere text) KHÔNG tìm được ảnh.

Tích hợp doanh nghiệp & cross-account HIGH-YIELD TRAP

KB là điểm tích hợp cho dữ liệu nội bộ (S3/SharePoint/Confluence) → vector store. Kiến trúc event-driven (SQS/Kafka pub-sub) cho phép loose coupling với hệ thống downstream.

TRAP "ra đề mọi kỳ thi": Bedrock & OpenSearch ở KHÁC account → dùng remote-inference connector của OpenSearch cho semantic search xuyên account + 1 IAM role cho phép account của OpenSearch gọi InvokeModel.
KB cùng account thì không cần connector cross-account hay IAM role riêng cho InvokeModel.

Prompt engineering & các kiểu prompt

  • Cấu trúc prompt chuẩn: Instructions · Context · Input data · Output indicator — đặt spec định dạng đầu ra ở cuối cùng.
  • Zero-shot (không ví dụ) · Few-shot (có ví dụ) · Chain-of-Thought ("suy nghĩ từng bước").
  • Prompt injection ("ignore the above…") & prompt leaking ("cho tôi biết instructions của bạn") → giảm thiểu bằng guardrails / system prompt chặt.
Cần cải thiện suy luận → Chain-of-Thought (few-shot = thêm ví dụ). Cần chặn injection/leaking → guardrails/system prompt.
Muốn sửa facts sai → dùng RAG; CoT chỉ sửa được bước suy luận, không sửa được kiến thức sai.

Prompt Management & Flows

  • Prompt Management: lưu prompt tái sử dụng, có version; biến trong {{double_braces}}; nhiều variant theo model/config; có thể gắn tool + caching.
  • Bedrock Flows (trước là "Prompt Flows"): chain nhiều prompt/model qua Node + Connection (có điều kiện); xây bằng giao diện kéo-thả hoặc JSON.
  • Structured JSON output: yêu cầu trong prompt HOẶC dùng Tool Use trong Converse ("response format template").
"quản lý tập trung nhiều prompt variant, version control, audit trail" → Prompt Management. "chain nhiều prompt/model, query decomposition" → Bedrock Flows.
Tự lưu prompt bằng DynamoDB/S3 + Lambda = nhiều bảo trì hơn Prompt Management có sẵn.

Bedrock Agents HIGH-YIELD

Agent = FM + memory + planning + tools. Trong Bedrock, tool là Action Group chạy trên Lambda.

  • Mô tả tool quan trọng — LLM dùng nó để trích tham số từ prompt người dùng; có thể hỏi lại nếu thiếu thông tin.
  • Định nghĩa tool qua OpenAPI schema hoặc bảng trong console. Agent cũng dùng được Knowledge Base (agentic RAG) và Code Interpreter.
  • Deploy qua alias (snapshot). Throughput: On-Demand (theo quota account) · Provisioned (mua sẵn công suất). Gọi bằng InvokeAgent.
Agent cần GỌI API ngoài + tìm tài liệu có audit trail → Bedrock Agent + Action Groups + Knowledge Base + trace events.
Cần session memory + identity + invoke event-driven VÀ đồng bộ ở scale lớn → AgentCore, không phải Bedrock Agent thường. Chuỗi bước cố định không cần LLM chọn tool → Step Functions.

Strands Agents

SDK agent mã nguồn mở của Amazon, code-first, ngang hàng OpenAI Agents SDK, CrewAI, LangGraph, Google ADK. Không bị khoá vào AWS. Tích hợp chặt với Bedrock/Lambda/Step Functions; multimodal; hỗ trợ MCP.

  • Định nghĩa tool tuỳ chỉnh bằng decorator @tool.
  • Vòng lặp: input → chọn tool → suy luận → thực thi → trả lời.
"code-first, single-agent tool-use loop, @tool decorator, MCP support" → Strands Agents SDK.

AWS Agent Squad TRAP

Framework mã nguồn mở (Python/TypeScript) chuyên routing: intent classification để phân luồng request tới đúng agent trong nhiều agent. Supervisor Agent điều phối, chia sẻ ngữ cảnh giữa các agent; tích hợp Bedrock Agents/Flows.

Amazon Bedrock AgentCore HIGH-YIELD

Deploy & vận hành agent serverless ở quy mô lớn — không cần Docker/ECR/ECS, hoạt động với BẤT KỲ framework nào.

  • Runtime: endpoint serverless (deploy qua ECR bằng CodeBuild); observability qua CloudWatch GenAI Observability.
  • Memory: managed short/long-term (Sessions+Events; Memory Records + Strategies).
  • Gateway: biến API/Lambda/Smithy/OpenAPI thành MCP tool; tự quản lý OAuth; chọn tool theo ngữ nghĩa.
  • Identity: định danh agent (giống Cognito pool) + OAuth tới Google/GitHub/Slack/Salesforce/Atlassian.
  • Tool built-in: Browser, Code Interpreter. Import Bedrock agent có sẵn bằng agentcore import-agent.
Bedrock Agent thường không có sẵn lớp identity/session-scaling như AgentCore. Step Functions + DynamoDB đòi hỏi tự dựng state thủ công.

AgentCore Policy (Cedar) TRAP

Chặn tool call tại Gateway, đánh giá theo policy — viết bằng ngôn ngữ Cedar (hoặc NLP/form).

  • Deny-by-default; validate theo ngữ cảnh (OAuth sub-claims, tham số tool). Enforce mode chặn thật; Log-only mode chỉ test.
  • Đánh giá NGOÀI code của agent — kiểm soát chi tiết ai/cái gì/khi nào.
IAM = quyền tài nguyên AWS, không kiểm tra tham số tool call. Guardrails = lọc nội dung, không phải authorization cho tool.

Model Context Protocol (MCP) HIGH-YIELD

"USB-C port cho AI apps" (Anthropic). Giao thức chuẩn agent↔tool. Data layer = JSON-RPC 2.0; transport = stdio hoặc HTTP streaming. Server expose tool, resource, prompt.

  • Tự deploy MCP server: Lambda (nhẹ/stateless), ECS/Fargate (phức tạp), API Gateway, hoặc AgentCore.
MCP server stateless/nhẹ → Lambda (function URL+SigV4, hoặc API Gateway HTTP API+Cognito OAuth) với Streamable HTTP transport.
ECS/Fargate dùng khi MCP server stateful/phức tạp, không phải Lambda đơn giản. REST API thường sẽ mất semantic của giao thức MCP.

OpenAPI cho tool

OpenAPI (tiền thân Swagger) chuẩn hoá định nghĩa function: tham số đầu vào, đầu ra, điều kiện lỗi cho từng tool. Dùng với Bedrock Action Groups: upload schema lên S3 hoặc chỉnh trong console.

Knowledge Base là nguồn retrieval, không phải định nghĩa tool có thể gọi.

Lambda cho GenAI

Serverless glue tự động scale. Nối agent↔tool, gọi FM theo yêu cầu, xử lý webhook, tổng hợp tuỳ chỉnh (model voting/weighting).

  • Lambda + Kinesis: batch size tới 10k record; payload tối đa 6 MB; xử lý shard đồng bộ — phải xử lý lỗi nếu không sẽ nghẽn shard.
Step Functions dùng khi orchestration nhiều bước có state/retry. ECS/Fargate dùng cho việc chạy dài/stateful.

Step Functions HIGH-YIELD TRAP

  • Điều phối workflow trực quan; retry/error handling built-in; Wait; thời gian chạy tối đa 1 năm.
  • States: Task, Choice, Wait, Parallel, Map (+Pass/Succeed/Fail). Map chạy từng bước theo item dataset song song.
  • GenAI: điều phối ReAct (reason+act), chain nhiều FM call, định tuyến động tới FM chuyên biệt, review/approval của model.
  • Tích hợp Bedrock: InvokeModel, CreateModelCustomizationJob (có thể chain + kèm guardrails).
  • Circuit breaker pattern (Lambda + DynamoDB) → fallback sang model khác khi 1 model bị down.
TRAP: Giới hạn 256 KB dữ liệu truyền giữa các state — dữ liệu lớn phải lưu ở S3/DynamoDB và truyền reference.

API Gateway HIGH-YIELD

  • Cổng vào cho Lambda/HTTP/AWS-service. Hỗ trợ WebSocket, throttling, API key, validate request/response, cache, sinh SDK.
  • Loại endpoint: Edge-optimized (mặc định, global qua CloudFront) · Regional · Private (VPC interface endpoint + resource policy).
  • Auth: IAM (nội bộ), Cognito (bên ngoài/mobile), Custom Authorizer.
  • Làm front cho model: usage plan, throttling (~10–50 rps), retry khi timeout, validate request + JSON schema cho token limit.
TRAP: Chứng chỉ custom-domain Edge-optimized PHẢI ở us-east-1; chứng chỉ Regional thì ở đúng region của API.

AppConfig — chọn FM động

Đổi cấu hình mà không cần deploy/restart; feature flag, allow/block list.

  • GenAI: đổi model không cần thay code qua config profile (lưu ở S3); rollout dần + rollback tự động theo CloudWatch alarm.
  • Validate config bằng JSON Schema (cú pháp) hoặc Lambda (logic).
Lambda env var đổi phải redeploy/restart — không "động". API Gateway stage variable phải cập nhật thủ công, không theo business rule per-request.

Giải kết nối: SQS · SNS · EventBridge

  • SQS: hàng đợi giải kết nối các tầng; scale worker theo ApproximateNumberOfMessages; access policy cho cross-account.
  • SNS: pub/sub fan-out — 1 message → nhiều subscriber (SQS, Lambda, HTTP, email/SMS).
  • EventBridge: schedule (cron) + event-pattern rule → Lambda/SQS/SNS/Step Functions; schema registry; resource-based policy cho cross-account bus; archive + replay.
S3 KHÔNG thể trigger Step Functions trực tiếp — phải qua EventBridge. SQS là điểm-điểm, không fan-out như SNS.

Triển khai model trên SageMaker HIGH-YIELD

  • Tuỳ chọn deploy: Real-time endpoint (on-demand) · Batch Transform (cả bộ dữ liệu) · Async endpoint (lớn/lâu, chịu được độ trễ) · Serverless.
  • Multi-model / multi-container endpoint; Inference Component cho phép mỗi model có scaling policy riêng.
  • Inference Pipeline, Neo (edge), auto-scaling, Shadow Testing.
Bedrock Provisioned Throughput là hosting FM có sẵn quản lý, không có pipeline train tuỳ chỉnh như SageMaker.

IAM cơ bản HIGH-YIELD

  • Least privilege: bắt đầu rộng ở dev, siết chặt dần; IAM Access Analyzer tự sinh policy least-priv từ hoạt động thực tế.

AWS KMS HIGH-YIELD

Nghe "encryption" → nghĩ ngay KMS. Được kiểm soát bằng IAM, audit qua CloudTrail, tích hợp sâu S3/EBS/RDS/SSM.

  • Loại khoá: Symmetric (AES-256, dùng bởi hầu hết service AWS) · Asymmetric (RSA/ECC; tải public key để mã hoá/ký ngoài AWS).
  • Quyền sở hữu: AWS Owned (free) · AWS Managed (free) · Customer Managed ($1/tháng, rotation tự động + on-demand) · Imported (chỉ rotation thủ công).
  • Envelope encryption: data key mã hoá dữ liệu; KMS mã hoá chính data key đó.
Secrets Manager lưu/rotate giá trị BÍ MẬT (mật khẩu/API key), không chỉ khoá mã hoá. CloudHSM = HSM single-tenant chuyên dụng, chỉ chọn khi cần FIPS 140-2 L3/toàn quyền khoá.
TRAP: SSE-KMS tính vào quota request/giây của KMS (GenerateDataKey/Decrypt) — S3 throughput cao có thể bị throttle vì lý do này.

Secrets Manager vs Parameter Store TRAP

  • Secrets Manager: lưu secret, auto-rotate (Lambda), tích hợp native với RDS, mã hoá KMS, replicate đa vùng.
  • SSM Parameter Store: cấu hình + secret (có KMS), rẻ hơn, KHÔNG có rotation built-in.
  • buildspec.yml của CodeBuild có thể lấy giá trị từ cả 2 (secrets-manager / parameter-store).
TRAP: Cần auto-rotate → Secrets Manager. Chỉ cần config rẻ, không rotation → Parameter Store.

Macie & bảo vệ dữ liệu

Comprehend là NER phát hiện/redact trên luồng văn bản, không phải scan bucket S3. Bedrock Guardrails chặn/mask lúc inference, không phải discovery dữ liệu đã lưu.

4Operational Efficiency & Optimization Domain 4 · 12% · 10 chủ đề

Token, chi phí, throughput, caching, latency, và độ ổn định khi gọi FM.

Ước tính & theo dõi token HIGH-YIELD

  • CountTokens API (Bedrock): trả số token của 1 request mà KHÔNG chạy nó — miễn phí, ước tính chi phí trước khi inference. Mỗi model tokenize khác nhau.
  • CloudWatch theo dõi InputTokenCount + OutputTokenCount, latency, invocation count, throttle, TTFT (Time To First Token, khi streaming).
Cost Explorer gán chi phí $ SAU khi đã phát sinh, không phải đếm token per-request trước — dùng CountTokens để ước tính TRƯỚC khi inference.

Giảm sử dụng token

  • Context pruning: chunk dữ liệu RAG, giới hạn số chunk retrieve, lọc theo metadata, tóm tắt/bỏ lịch sử chat cũ.
  • Giới hạn response: maxTokens, gài độ dài vào prompt ("≤50 từ"), few-shot để định hình độ dài, JSON để ép format/độ dài.
  • Nén prompt: dùng model nhỏ để tóm tắt chat/tài liệu dài trước; dùng Knowledge Bases thay vì dán cả tài liệu vào prompt.
Provisioned Throughput mua thêm công suất nhưng vẫn trả tiền mỗi token — nên cắt token TRƯỚC (pruning/maxTokens) rồi mới tính đến mua thêm capacity.

Chọn model tiết kiệm chi phí HIGH-YIELD

Không phải lúc nào cũng cần model lớn nhất. Nếu "sự thông minh" nằm ở RAG + tool, model nhỏ thường đã đủ; dùng model nhỏ cho tiền xử lý (tóm tắt/phân loại/chunk).

  • Intelligent Prompt Routing (tính năng Bedrock): định tuyến theo độ phức tạp câu hỏi tới model nhỏ/vừa/lớn. Cũng có thể tự xây bằng Flow có điều kiện, Lambda, Agent Squad, hoặc Strands (router agent với tool "độ phức tạp").
  • Đo price:performance: Bedrock Evaluations so sánh tính năng + đếm token; gán chi phí bằng Cost Explorer.
Latency-optimized inference chỉ tăng tốc 1 model, KHÔNG chọn model rẻ hơn theo độ phức tạp — cần Intelligent Prompt Routing cho bài toán tối ưu chi phí.

Sử dụng tài nguyên & throughput HIGH-YIELD TRAP

  • Bedrock Batch Inference: gửi nhiều prompt qua S3, nhận response cũng ở S3 (rẻ, khối lượng lớn, không real-time).
  • Provisioned Throughput: mua theo token / Model Unit (MU) để có hiệu năng cao ổn định liên tục. Lập kế hoạch capacity từ TPM/RPM qua Service Quotas.
  • Tensor parallelism chia trọng số LLM qua nhiều GPU (dùng bộ nhớ hiệu quả hơn). Auto-scaling qua serverless (Lambda, Bedrock, OpenSearch Serverless, AgentCore).
TRAP: Provisioned Throughput là BẮT BUỘC cho model tuỳ chỉnh (fine-tuned/imported) — phải truyền ARN của provisioned model làm modelId lúc inference.
Batch Inference rẻ nhưng không real-time — cần capacity ổn định độ trễ thấp thì chọn Provisioned Throughput. Cross-Region Inference KHÔNG tương thích với Provisioned Throughput — chỉ chọn 1.

  • Dùng response streaming, gọi song song (Step Functions / multi-agent), tính trước các câu hỏi có thể đoán trước.
  • Giữ prompt ngắn gọn; đặt nội dung quan trọng lên đầu (phòng khi bị cắt); chia nhỏ task phức tạp.
Cross-Region Inference dàn tải qua nhiều Region để tăng throughput/tính sẵn sàng, không phải TTFT của 1 request. Provisioned Throughput ổn định capacity dưới tải nhưng không phải "nút vặn" độ trễ — cần thêm performanceConfig=optimized để giảm TTFT.

Tham số inference TRAP

  • Temperature: độ ngẫu nhiên (0 = deterministic, 1 = sáng tạo).
  • Top_p (nucleus sampling): ngưỡng xác suất cho token ứng viên — chỉ chọn temperature HOẶC top_p, không cả hai.
  • Top_k: số lượng token ứng viên để sample.
  • A/B test thay đổi tham số bằng Bedrock Evaluations hoặc CloudWatch Evidently.
TRAP: Tăng temperature để "sửa hallucination" là SAI — tăng temperature làm TĂNG ngẫu nhiên và hallucination. Muốn chính xác hơn → giảm temperature hoặc dùng RAG/CoT.

Resilience: backoff & connection pooling TRAP

  • Exponential backoff cho retry: bắt đầu 100ms, nhân đôi (×2), tối đa 3–5 lần, cộng ±100ms jitter (tránh retry đồng loạt). Cấu hình trong AWS SDK client.
  • Circuit breaker: ngăn lỗi lan truyền khi bị throttle liên tục.
  • Connection pooling (HTTP client): giữ 10–20 kết nối mở/instance, TTL 60–300s — tái sử dụng thay vì tạo mới mỗi request.
Tăng Model Unit (Provisioned Throughput) chỉ giải quyết thiếu hụt capacity DÀI HẠN, quá tay cho spike tạm thời — spike tạm thời nên thêm backoff+jitter. Nếu provisioned capacity vẫn rảnh mà bị throttle, lỗi thường là modelId sai (phải dùng ARN), không phải thiếu backoff.

5Testing, Validation & Troubleshooting Domain 5 · 11% · 8 chủ đề

Các cách đánh giá FM HIGH-YIELD

  • Human: tốt nhất cho UX, độ liên quan, sáng tạo, xử lý tình huống bất ngờ (GenAI non-deterministic, khó đo).
  • Benchmark datasets: cặp prompt/answer do SME tạo → đo độ chính xác, tốc độ, khả năng mở rộng, truy xuất context; dùng cho leaderboard. Chỉ tốt bằng dữ liệu test.
  • LLM-as-a-judge: 1 model đáng tin cậy chấm điểm response — rẻ hơn; rủi ro nếu judge chia sẻ điểm yếu với model đang test. Tốt để test model nhỏ/hiệu quả.
  • Hybrid: kết hợp human + benchmark để lộ ra giới hạn của nhau.
Cần cả quy mô lớn + đánh giá tinh tế → Hybrid: LLM-as-a-judge sàng lọc tự động + human review case biên/quan trọng.
Human-only không scale được. Chỉ dùng benchmark dataset cố định sẽ bỏ sót UX/sáng tạo/input bất ngờ.

Metric: ROUGE vs BLEU vs BERTScore HIGH-YIELD TRAP

MetricĐoTốt nhất cho
ROUGERecall của n-gram trùng (ROUGE-N) / LCS (ROUGE-L)Tóm tắt (summarization)
BLEUPrecision của n-gram + brevity penaltyDịch máy (machine translation)

TRAP kinh điển: đề hay hoán đổi 3 metric này làm distractor. Nhớ nhanh: ROUGE = Recall, BLEU = Brevity/dịch, BERTScore = BERT/ngữ nghĩa.

Bedrock Model Evaluations HIGH-YIELD

  • Automatic: task type có sẵn (generation, summarization, Q&A, classification) + metric built-in.
  • Human-based: người so sánh 2 model trên bộ prompt của bạn; work team qua Cognito / Ground Truth / Amazon A2I.
  • LLM-as-a-judge: model đánh giá + model sinh; thêm custom metric qua judge prompt.
  • Metric built-in: correctness, helpfulness, conciseness, instruction-following, faithfulness, relevance, coherence, refusal, goal success, độ chính xác chọn tool, harmfulness, stereotyping.
SageMaker Clarify đo bias/fairness xuyên nhóm nhân khẩu học, không phải Bedrock model eval job. fmeval/Ragas mã nguồn mở đòi hỏi tự viết notebook SageMaker — nhiều overhead hơn eval job có sẵn của Bedrock.

RAG evaluation jobs

  • Retrieve-only: chỉ đo retrieval — relevance & coverage.
  • Retrieve-and-generate: đo luôn câu trả lời — correctness, completeness, helpfulness, logical coherence, faithfulness (bám sát nội dung truy xuất), citation precision.
  • Cung cấp bộ prompt dataset ở S3 (JSON-lines) kèm reference response/context. Tam giác quan trọng: Answer Relevance · Context Relevance · Groundedness.
Retrieve-only KHÔNG chấm điểm chất lượng câu trả lời — chỉ đo retrieval.

Deployment validation

GenAI non-deterministic → unit test không đủ. Dùng synthetic end-to-end user workflow trước/sau khi deploy.

  • Công cụ: CloudWatch synthetic canary, Step Functions, EventBridge, Lambda; lưu kết quả ở S3/Athena, xem ở QuickSight.
  • Validate output AI: tỷ lệ hallucination, semantic drift, faithfulness, độ nhất quán response (biến động trong khoảng chấp nhận được).
Unit test-only không đủ vì GenAI non-deterministic. Bedrock Model Evaluation (batch) là chấm điểm offline, không phải phát hiện drift real-time.

CloudWatch cho GenAI HIGH-YIELD

  • Log (group/stream, mã hoá được bằng KMS) → S3/Kinesis/Lambda/OpenSearch. Logs Insights = query engine (không phải real-time).
  • Xuất real-time = Logs Subscriptions (Kinesis/Firehose/Lambda); export sang S3 mất tới 12h.
  • Alarm (OK/INSUFFICIENT_DATA/ALARM); Composite Alarm giảm nhiễu (AND/OR).
  • Theo dõi: hiệu quả prompt, latency, tỷ lệ lỗi, tỷ lệ hallucination, token-burst bất thường, response drift, log invocation Bedrock, cost anomaly.
AWS X-Ray là trace từng request qua nhiều service, không phải anomaly/baseline alarm. CloudTrail là audit API call, không phải performance metric. SageMaker Model Monitor là ML feature/data drift, nặng hơn — CloudWatch đã đủ cho token/cost anomaly.

AWS X-Ray (tracing) TRAP

  • Trace request end-to-end xuyên microservice; segment + subsegment + annotation; trace mọi request hoặc theo % mẫu.
  • Kích hoạt: import X-Ray SDK + chạy daemon (Lambda/nhiều service tự chạy sẵn). Hoạt động với Lambda, ECS, ELB, API Gateway, EC2, Beanstalk.
  • Bảo mật: IAM cho authz, KMS cho mã hoá at rest.
TRAP: X-Ray trên Lambda không chạy? Cần IAM role có AWSX-RayWriteOnlyAccess, SDK đã import, VÀ Active Tracing đã bật.
CloudWatch là metric/alarm tổng hợp, không phải trace từng request. CloudTrail là audit event API, không phải latency tracing xuyên service.

AgentCore Evaluations & Observability

Đánh giá hiệu năng task, edge case, độ nhất quán của agent; tích hợp Strands, LangGraph, OpenTelemetry, OpenInference.

  • Trực quan hoá trong CloudWatch (GenAI Observability Insights); alarm như thường; cross-region inference giúp tăng resilience.
  • CloudTrail theo dõi API call Bedrock; CloudWatch RUM đo hiệu năng end-to-end của app mobile GenAI.
AWS X-Ray là tracing hạ tầng cấp request, không phải eval/trace reasoning của agent. CloudTrail log API call để audit, không phải trace từng bước của agent.
